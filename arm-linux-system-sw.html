Userspace부터 Device Tree까지 연결한
ARM Linux 시스템 소프트웨어

QEMU ARM64에서 Buildroot 기반 Linux를 부팅하고 Device Tree 기반 플랫폼 드라이버와 문자 디바이스를 구현했습니다. 이어서 시스템 정보와 장치 이벤트를 하나의 큐로 처리하는 멀티스레드 시스템 모니터링 프로그램까지 연결했습니다.

Role

01

문제 상황과 목표

Linux 드라이버와 Device Tree를 개별 기능으로 학습하는 것만으로는 애플리케이션의 요청이 커널과 하드웨어 표현까지 어떻게 이어지는지 파악하기 어려웠습니다. ARM64 Linux 부팅부터 커널 드라이버, 장치 이벤트 처리와 userspace 프로그램까지 하나의 흐름으로 연결하는 것을 목표로 삼았습니다.

02

담당 범위

QEMU와 Buildroot 환경 구성, misc character device와 원형 버퍼, Device Tree 기반 플랫폼 드라이버, poll/wait queue 연동, 멀티스레드 시스템 모니터링 프로그램의 설계·구현·빌드·배포·문제 추적을 직접 수행했습니다.

03

단계별 구현

  1. 환경 구성Buildroot로 Linux kernel과 BusyBox root filesystem을 구성하고 QEMU virt에서 ARM64 Linux 부팅
  2. 문자 디바이스miscdevice와 256바이트 원형 버퍼, wrap-around, 부분 읽기·쓰기와 EAGAIN 처리
  3. 플랫폼 연결Device Tree compatible matching과 GPIO descriptor 획득 및 자원 해제 경로 구현
  4. 이벤트 처리wait queue와 poll을 연결해 읽기·쓰기 가능 상태 변화 전달
  5. 스레드 연동두 생산자와 한 소비자가 16개 항목의 bounded queue를 공유하도록 구성

DEBUGGING

등록된 드라이버의 probe가 실행되지 않은 원인 추적

드라이버 코드에서 시작해 실제 guest가 사용한 Device Tree와 QEMU 부팅 인자까지 확인 범위를 넓혔습니다.

  1. 01

    현상 확인

    플랫폼 드라이버 등록 로그는 있었지만 probe가 호출되지 않았고 /dev/mydevice도 생성되지 않았습니다.

  2. 02

    실행 환경 대조

    소스의 Device Tree 노드뿐 아니라 QEMU가 부팅 시 실제로 사용한 DTB와 실행 옵션을 확인했습니다.

  3. 03

    원인 확인

    수정한 qemu-mydevice.dtb가 -dtb 옵션으로 전달되지 않아 guest에 matching 대상 platform device가 존재하지 않았습니다.

  4. 04

    수정 및 확인

    QEMU 실행 명령에 DTB를 명시한 뒤 probe 로그와 /dev/mydevice 생성을 확인했습니다.

LEARNING

드라이버 등록과 장치 결합을 구분

platform_driver_register()의 성공은 드라이버 등록을 의미할 뿐, Device Tree에 일치하는 장치가 존재해 probe가 실행되었다는 뜻은 아닙니다. 문제 범위를 코드 밖의 부팅 구성과 실제 하드웨어 표현까지 확장해야 한다는 점을 확인했습니다.

RESULT & LIMITS

전체 경로의 기능 동작과 종료 상태 확인

플랫폼 드라이버 binding 후 시스템 정보와 장치 이벤트가 큐를 거쳐 소비자에게 전달되는 흐름을 확인했습니다.

01

시스템 정보 수집

/proc/stat과 /proc/meminfo에서 CPU·메모리 정보를 30회 수집했습니다.

02

장치 이벤트 전달

/dev/mydevice에 기록한 hello 5바이트가 poll과 read를 거쳐 소비자에게 전달되었습니다.

03

종료 상태

모든 생산자 종료 후 큐 잔여 데이터와 활성 생산자 수가 각각 0인 것을 확인했습니다.
