Device Tree, and virtual hardware

Booted a Buildroot-based ARM64 Linux system on QEMU, implemented a Device Tree-matched platform driver and character device, and connected them to a multithreaded system monitoring program that processes system statistics and device events through one queue.

01

Problem and goal

Learning Linux drivers and Device Tree as isolated features did not make the complete execution path clear. I set out to connect ARM64 Linux boot, the kernel driver, device-event handling, and the userspace program as one observable system flow.

02

Scope

I configured the QEMU and Buildroot environment, implemented the misc character device and ring buffer, integrated the Device Tree platform driver with poll and wait queues, and designed, built, deployed, and debugged the multithreaded system monitoring program.

03

Implementation stages

  1. Bring-upBuilt the Linux kernel and BusyBox root filesystem with Buildroot and booted ARM64 Linux on QEMU virt
  2. Character deviceImplemented miscdevice, a 256-byte circular buffer, wrap-around, partial I/O, and EAGAIN handling
  3. Platform integrationMatched the driver through Device Tree and managed the GPIO descriptor acquisition and release path
  4. Event handlingConnected wait queues to poll readiness for readable and writable state changes
  5. Thread integrationConnected two producers and one consumer through a 16-entry bounded queue

DEBUGGING

Tracing why the registered driver's probe did not run

The investigation expanded from driver code to the Device Tree actually used by the guest and the QEMU boot arguments.

  1. 01

    Observed symptom

    The platform driver registration message appeared, but probe was not called and /dev/mydevice was not created.

  2. 02

    Compared the runtime setup

    I checked not only the Device Tree source but also the DTB and command-line options used for the actual QEMU boot.

  3. 03

    Found the cause

    The modified qemu-mydevice.dtb was not passed with the -dtb option, so no matching platform device existed in the guest.

  4. 04

    Applied and checked the fix

    After adding the DTB to the QEMU command, I confirmed the probe log and /dev/mydevice creation.

LEARNING

Separating driver registration from device binding

A successful platform_driver_register() only registers the driver; it does not prove that a matching device exists or that probe has run. The investigation therefore needs to include boot configuration and the hardware description used at runtime.
