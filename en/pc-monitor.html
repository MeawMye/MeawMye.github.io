PERSONAL PROJECT · STM32

Real-time PC resource visualization
on an STM32 LCD

CPU, RAM, and network usage were measured on the PC and transmitted to the UART to display recent status changes on the STM32F729I-DISCO's LCD.

01

Problem

During full-screen operation, you had to switch screens to check system status. We wanted to create a device that could continuously check CPU, RAM, and network changes on a separate display.

02

My Role

We implemented the entire flow from Python-based PC resource measurement, port search, UART transmission to STM32 reception interrupt, packet parsing, history management, and LCD graph output.

03

Approach

  1. MeasurementCollect CPU/RAM usage and network throughput with psutil
  2. TransmissionSend a text frame with defined fields and boundaries to UART
  3. ReceptionAssemble the frame with a 1-byte interrupt and signal completion to the task
  4. StorageKeep the most recent 100 samples in a fixed-size circular buffer
  5. VisualizationConvert measured values ​​to LCD coordinates and output CPU/RAM/NET graph

PROTOCOL

readable text frame

$CPU:35,RAM:62,NET:120#

$and #identified frame boundaries in the byte stream. It is easy for humans to read, making serial debugging simple, but checksums and strict input range verification leave room for improvement.

HISTORY

fixed size circular buffer

cpu[100]  uint8_t
ram[100]  uint8_t
net[100]  uint16_t

Provides chronological order from oldest to newest values, with fixed memory usage and no data movement.

DEBUGGING

Isolate the causes of LCD Bring-up failure step by step

Instead of viewing HardFault and screen blanking as a single problem, we divided the initialization path into four steps.

  1. 01

    Clock

    We compared the PLL settings with the board example to check for possible SystemClock instability.

  2. 02

    Timebase

    TIM6 based HAL timebase conflict identified and isolated with SysTick.

  3. 03

    SDRAM

    BSP_SDRAM_Init() was used to compare the external memory initialization path.

  4. 04

    DSI

    The panel ON command and initialization order have been rearranged to fit the board example flow.

Verification result

LCD initialization and output worked normally, and screen updates were maintained even after FreeRTOS was started.
